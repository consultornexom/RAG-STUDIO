# Checklist de validación visual — RAG STUDIO (4 pestañas)

Antes de empezar: registra una fuente real (PDF/DOCX/TXT/Markdown) que tengas a mano, aparte del plan de estudios ya usado en los scripts. Así validamos con un documento distinto al que ya se probó por línea de comandos.

**Nuevo, 2026-07-29 — esquema de color de la interfaz:** este entorno de construcción no tiene acceso a las bibliotecas gráficas del sistema (falta `libEGL`), así que la hoja de estilos y el color de estado (`ui/theme.py`) no se pudieron verificar con una captura de pantalla real. Al abrir la aplicación, confirmar: (1) toda la ventana tiene una identidad visual consistente (fondo gris claro, botones y pestaña activa en azul, tarjetas/agrupadores con borde); (2) en la lista de Proyectos, un proyecto en estado "aprobado" o "liberado" se ve con texto verde, uno "en_construccion"/"en_pruebas" en azul; (3) en Fuentes, una fuente "rechazado" o "vencido" se ve en rojo; (4) en el reporte de Liberación, "Aprobada" se ve en verde y "Bloqueada" en rojo, con los símbolos ✔/✘ del mismo color. En todos los casos el texto original debe seguir ahí (el color solo refuerza, nunca reemplaza el texto).

**Nuevo, 2026-08-01 — detección de Tesseract en Windows (auditoría de madurez ronda 5):** este entorno de construcción es Linux, así que la lógica nueva de `infrastructure/extraction/ocr_engine.py` que busca el binario de Tesseract en las rutas por defecto de Windows (o en `RAGSTUDIO_TESSERACT_PATH`) nunca se ejecutó de verdad, solo se revisó por lectura de código. En la máquina Windows donde se está probando la herramienta, confirmar: (1) si Tesseract ya está instalado con el instalador de UB-Mannheim en su ruta por defecto, extraer un PDF escaneado debe funcionar sin configuración adicional; (2) si Tesseract no está instalado o no se encuentra, el aviso de error debe mencionar el instalador de Windows y la variable `RAGSTUDIO_TESSERACT_PATH` (no el comando de `apt` de Linux); (3) definir `RAGSTUDIO_TESSERACT_PATH` con la ruta completa a `tesseract.exe` debe resolver el problema sin reinstalar nada.

**Nuevo, 2026-08-01 — aviso emergente al terminar procesos de fondo (validación de notificaciones, a pedido del consultor):** en Ingesta, confirmar que al terminar con éxito "Ejecutar pipeline completo", "Extraer texto", "Fragmentar", "Indexar" y "Comparar modelos" aparece una ventana emergente "Listo" (no solo el texto de estado) -- probar específicamente cambiando a otra pestaña mientras el trabajo corre, para confirmar que el aviso sigue apareciendo aunque el usuario ya no esté viendo Ingesta. Confirmar que "Buscar" (textual/híbrida/semántica) NO muestra ese emergente (a propósito, ver bitácora). En Diseño conversacional, confirmar el mismo aviso al terminar una simulación. En Calidad, confirmar el mismo aviso al terminar "Ejecutar evaluación". En los tres casos, si el trabajo falla o se cancela, el comportamiento no debe haber cambiado (ya mostraba emergente de error, o solo texto de estado si fue cancelación).

## 1. Proyectos

- Crear un proyecto nuevo con nombre válido → debe aparecer en la lista como `nombre [inicial] (id)`.
- Intentar crear uno con nombre vacío o solo espacios → el diálogo no debe crear nada (ni error raro, ni proyecto en blanco en la lista).
- Seleccionar el proyecto → confirmar que las pestañas Fuentes/Metadatos/Ingesta "se activan" (dejan de mostrar "selecciona un proyecto").
- Pulsar "Archivar" sin nada seleccionado → no debe pasar nada (ni crash).
- Archivar el proyecto de prueba → el estado en la lista debe cambiar a `[archivado]`.
- Exportar el proyecto (botón "Exportar…") → elegir una ruta `.agentproj`, confirmar que aparece el mensaje con el conteo de archivos exportados y que el archivo se creó de verdad en disco.
- Importar ese mismo `.agentproj` → debe aparecer un proyecto nuevo en la lista (o el mismo, según cómo lo hayas exportado) y quedar seleccionado automáticamente.
- Intentar importar un archivo que no sea `.agentproj` (renombra cualquier otro archivo con esa extensión) → debe mostrar un error claro, no un traceback crudo.
- (Verificación de fondo no bloqueante: ver el paso "Ejecutar pipeline completo" en la sección 4 de Ingesta — mientras corre, mueve el mouse y cambia de pestaña; la ventana no debe congelarse.)

## 5. Widget web del runtime de producción (ADR-002, Fase 3)

**Actualizado, Ronda 10 (2026-08-11) -- corregido un bug real que impedía que el widget se dibujara.** La auditoría de la Ronda 10 encontró que `document.currentScript` (usado para leer `data-project-id`/`data-api-base`/`data-widget-token`) se leía dentro de `init()`, que se difiere a `DOMContentLoaded` para cualquier `<script>` sin `defer`/`async` colocado antes de que termine el parseo de la página -- exactamente el caso normal de uso, y el mismo snippet que genera "Exportar paquete de entrega al cliente…". Se corrigió capturando `document.currentScript` en el ámbito síncrono del propio `<script>`, y se verificó ejecutando el JS real con Node (`tests/integration/test_widget_script_currentscript_fix.py`, construye un DOM mínimo que reproduce el escenario exacto) -- pero esa prueba, aunque real, sigue sin ser un navegador de verdad. Este entorno de construcción no tiene acceso a un navegador real ni a Internet sin restricciones (no se pudo instalar un Chromium headless para automatizar esta prueba), así que el widget en sí -- el botón flotante, el panel de chat, el aislamiento de estilos con Shadow DOM -- solo se verificó por lectura de código, la prueba de Node ya mencionada, y pruebas de servidor (`tests/integration/test_widget_channel.py`: `GET /widget.js` se sirve sin autenticación, con CORS configurable). Falta la prueba real en un navegador:

1. Publica una instantánea de un proyecto real desde la pestaña de Liberación ("Publicar instantánea…").
2. Instala el extra de la API (`pip install -e .[api]`) y arráncala en local: `RAGSTUDIO_HOME=<tu instalación> RAGSTUDIO_API_KEY=demo uvicorn interfaces.api.app:app --port 8000`.
3. Crea un HTML de prueba en tu máquina con: `<script src="http://localhost:8000/widget.js" data-project-id="TU_PROJECT_ID" data-api-base="http://localhost:8000" data-api-key="demo"></script>` y ábrelo con el navegador (doble clic al archivo `.html` basta).
4. Confirma que aparece el botón flotante 💬 abajo a la derecha, que al hacer clic se abre el panel de chat, y que al escribir una pregunta relacionada con el proyecto aparece primero tu mensaje y luego la respuesta del asistente.
5. Si la pregunta coincide con una intención de tipo "responder" (sin variables faltantes), confirma que la respuesta lista los fragmentos recuperados con el prefijo "Esto encontramos en la documentación:" -- nunca debe aparecer un texto que "suene" a una respuesta redactada por una IA, porque este runtime no genera lenguaje natural (a propósito, ver ADR-001).
6. Cambia la página de prueba a otro origen (por ejemplo, sírvela con `python -m http.server 9000` en vez de abrirla como archivo) sin agregar `data-api-key` correcto o sin que el servidor tenga configurado `RAGSTUDIO_WIDGET_ALLOWED_ORIGINS` con ese origen -- confirma en la consola del navegador que la solicitud falla por CORS (esto es lo esperado sin configurar el origen, no un bug).
